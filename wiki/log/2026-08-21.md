## [2026-08-21] repair | Runs that did nothing were reporting success

An audit of both team flows found the federation's automated layer largely inert, and
invisible because every skipped job exited 0.

**The weekly reflection** has produced nothing in any spoke. `ANTHROPIC_API_KEY` is unset, so
the job guards, skips and passes; two spokes had reported success every Friday since 14 August
with no reflection written and no `wiki/reflections/` directory to show for it. The guard's own
comment argues against failing weekly — *"a weekly red X trains people to ignore CI"* — and that
is right for a job that costs money and is genuinely optional. So the outcome is now stated on
the run page itself via the step summary, and the notice was raised to a warning. Green, but no
longer silent.

## [2026-08-21] rebuild | The down-flow reads every declared commons, not just one

The federation's up-flow has read `design/federation.json` since the second commons was
created; the down-flow never did. `sync-commons.yml` cloned a single hardcoded repo into a flat
`.commons/export`, so a wiki declaring two commons silently synced one of them — the limitation
noted when the second commons was declared, now closed.

Both directions now read the same declaration. The workflow loops over `contributes_to` and
caches each at `.commons/<name>/export/`, which is the layout `contribute.py` has always
preferred for its collision check. There is deliberately **no `COMMONS_REPO` variable**: a
wiki's place in the graph is declared once, in the repo, and a second place to configure it is a
second place for it to be wrong.

`commons_report.py` follows — it reports each commons separately instead of assuming one, and
still falls back to the flat path so a cache written by an older sync is a degraded read rather
than a broken one.
